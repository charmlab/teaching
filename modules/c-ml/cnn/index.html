Convolutional Neural Networks

Backpropagation ended with a blank cheque: it can train any weights we care to wire up. This lecture is about wiring them up well. Feed an image to the fully connected networks we already have and the parameter count explodes, while everything we know about images, that patterns are local, that the same pattern repeats, that a small shift should not matter, gets thrown away. Two ideas, local receptive fields and weight sharing, fix both problems at once, and their combination has a name: convolution. This is Part I, the foundations, with an interactive figure for every concept.

0. The hook: 120,000 numbers before we start

Count the cost of doing what we already know. A modest colour photo is $200 \times 200$ pixels with three colour channels, so flattening it into the input vector our networks expect gives $200 \times 200 \times 3 = 120{,}000$ values. Now connect that vector to a single fully connected hidden layer of 1,000 units, exactly the way the last three lectures would. Every unit sees every pixel, so the layer needs $120{,}000 \times 1{,}000 = 120{,}000{,}000$ weights, plus a thousand biases, before it has produced a single feature. One layer. A thumbnail-sized image.

And here is the insult on top of the injury: all 120 million of those weights are spent learning nothing about what an image is. A fully connected layer treats its input as an arbitrary list of numbers. Shuffle every image in the dataset with the same fixed pixel permutation and the fully connected network would train exactly as well, because it never knew pixel (3, 4) sat beside pixel (3, 5) in the first place. We are paying an enormous price for a model that cannot see structure we get for free. Feel the explosion yourself:

Fig 0.1, the parameter-count shock. Slide the image size and the layer width: the fully connected count (orange) grows with the square of the image side, while the convolutional count (green) for the same width does not move, because it depends only on the kernel size and the number of filters. Both counts are computed live from the formulas in section 4.

The green line is where this lecture is going. There has to be an architecture that spends its parameters on the structure of images instead of in spite of it, and by section 4 you will be able to compute both of those counts by hand.

1. What makes images special

Why is object recognition even hard? Because the visual world is brutal to a classifier: there are thousands of object classes, huge variation within every class, one "dog" is a chihuahua in sunlight and another is a husky in snow, and the same object appears against endlessly diverse scenes. The neural networks lecture gave us the right response to hard inputs: learn a representation, raw input to features to decision, instead of hand-crafting features. Backpropagation gave us the training algorithm. What is missing is an architecture that makes the feature-learning problem easier by respecting what images are.

Because images are not arbitrary lists of numbers. They come with three regularities so reliable you can bet an architecture on them:

🔍
Locality
Nearby pixels form meaningful patterns. An edge, a corner, a patch of fur: each lives in a small neighbourhood, not spread across the whole frame.
🔁
Reuse
The same pattern can appear in many locations. An edge detector that works in the top-left corner is exactly the detector you want everywhere else.
🎯
Stability
Small shifts should not change the prediction. Move the cat two pixels left and it is still a cat, and the model should not have to relearn that fact.

Hold a fully connected layer up against that list and it fails all three tests. It has no notion of "nearby", so locality is invisible to it. It learns a separate weight for every pixel-unit pair, so a pattern learned in one corner teaches it nothing about the same pattern anywhere else. And a two-pixel shift scrambles which weights see which values, so stability has to be memorized example by example instead of being built in. The rest of this lecture builds the architecture that passes all three tests, and the big idea is worth stating up front: CNNs work because they build these assumptions about images directly into the architecture. Locality, weight sharing, translation robustness. Keep those three phrases; the summary will return to them as the CNN inductive bias.

2. Two ideas: local receptive fields and weight sharing

First, a definition we will use constantly. The receptive field of an activation is the region of the input image that influences it. For a fully connected unit, the receptive field is the entire image, which is exactly the problem.

Idea 1: local receptive fields. Connect each hidden unit only to a small patch of the image, say a few pixels on a side, instead of to everything. This is not just a parameter-saving trick, it encodes a prior: useful visual patterns, edges, corners, textures, object parts, are local. It also respects that nearby pixels are more related to each other than distant ones. One unit looking at a small patch needs a small patch worth of weights, not 120,000 of them.

Idea 2: weight sharing. The object can be anywhere in the frame, so a pattern worth detecting at one location is worth detecting at every location. Instead of giving each patch its own private weights, reuse the same local weights across all locations. Now the number of weights does not depend on how many locations there are at all, which is how the green line in Fig 0.1 stays flat.

What do the shared weights actually do? They act as pattern detectors. A neuron computes

$$ z = f(w^\top x + b) $$

where $x$ is the input patch, $w$ is the weight pattern, $b$ is a bias, and $f$ is an activation function. The dot product $w^\top x$ is large exactly when the patch aligns with the weight pattern. Take $w = [1,1,1,1,1,1]$, a detector for "uniformly bright". The patch $x_1 = [5,5,5,5,5,5]$ gives $w^\top x_1 = 30$, while the half-lit patch $x_2 = [0,0,0,5,5,5]$ gives only $w^\top x_2 = 15$. The aligned patch activates twice as strongly. Build your own detector and test it:

Fig 2.1, weights as pattern detectors. Click cells to edit the patch $x$ and the filter $w$; the response $z = w^\top x + b$ is computed live, term by term. Load the lecture's two patches and watch the aligned one score 30 against 15.

Check: design a detector that fires on a step, not on brightness

The all-ones filter scores 15 on the step patch $[0,0,0,5,5,5]$ but it scores 30 on a flat bright patch, so it is really a brightness detector. Design a $w$ that responds strongly to the dark-to-bright step and gives exactly zero on any flat patch.

Answer. $w = [-1,-1,-1,1,1,1]$. On the step: $-0-0-0+5+5+5 = 15$. On a flat patch $[c,c,c,c,c,c]$: $-3c + 3c = 0$ for every $c$, so uniform brightness is invisible to it. It answers "is the right half brighter than the left half", which is the beginning of an edge detector, and section 3 slides exactly this kind of filter across a whole image. Verify both numbers in Fig 2.1.

So the plan is set: small filters (Idea 1) reused everywhere (Idea 2), each one a learned pattern detector, with backpropagation from last lecture doing the learning. What we need now is the operation that applies one filter at every location of an image in a single, well-defined sweep. That operation is convolution.

3. Convolution: the sliding dot product

Convolution implements locality plus weight sharing in one move: take a small kernel (also called a filter), a little array of weights $w$, slide it over the input, and at each position compute how strongly the local patch matches the filter. The grid of responses it produces is called a feature map: a map of where in the input the filter's pattern was found. Every entry of that map is a dot product between the same learned filter and one local patch.

One dimension first

For an input signal $x$ and a kernel $w$ of length $k$, the convolution is

$$ (x * w)[t] = \sum_{\tau=0}^{k-1} x[t - \tau]\, w[\tau] $$

Read it slowly: to produce output element $t$, take the kernel entries $w[\tau]$ and multiply each against the input entry $\tau$ steps back from $t$, then add. Near the ends of the signal the index $t - \tau$ runs off the array, so we zero-pad $x$, extend it with zeros, which adds no new information. Two mental pictures both compute the same thing: flip-and-filter, where you reverse the kernel, slide it along the input, and take dot products, and translate-and-scale, where each input entry $x[i]$ stamps a copy of the whole kernel at position $i$, scaled by $x[i]$, and the copies add up.

Worked by hand: [1, 1] * [2, −2] = [2, 0, −2]

Let $x = [1, 1]$ and $w = [2, -2]$. Both have length 2, so the full output has $2 + 2 - 1 = 3$ entries, and out-of-range values of $x$ are zero:

y[0] = x[0] w[0]             = (1)(2)         = 2
y[1] = x[1] w[0] + x[0] w[1] = (1)(2) + (1)(−2) = 0
y[2] = x[1] w[1]             = (1)(−2)       = −2

So $[1,1] * [2,-2] = [2, 0, -2]$. Notice what the kernel $[2,-2]$ is: a difference detector. Sliding it across the constant signal $[1,1]$ reports "change on the way in, nothing in the middle, change on the way out."

Two properties to file away. Convolution is commutative, $x * y = y * x$, so it does not matter which array you call the signal and which the kernel. And it is linear:

$$ a * (\lambda_1 b + \lambda_2 c) = \lambda_1\, (a * b) + \lambda_2\, (a * c) $$

which is worth remembering for exactly the reason linear layers were worth worrying about: a stack of linear operations is still linear. Section 5 cashes that observation in. Now watch the sliding sum happen, step by step, on the worked example:

Fig 3.1, the 1-D convolution stepper. At each step the flipped kernel sits under the padded input, the aligned pairs multiply (shown term by term), and the sum lands in the output. Step through $[1,1] * [2,-2]$ and check it against the worked math above, then try the longer example.

That is the elementwise product. Convolution slides one array across the other, so the ends overlap partially and the output is longer than either input.

Two dimensions: the same idea, over patches

Images are 2-D grids, so the kernel becomes a small grid too, and the sum runs over both directions:

$$ (x * w)[i, j] = \sum_s \sum_t x[i - s,\, j - t]\, w[s, t] $$

In practice you should think of it exactly as section 2 set up: place the kernel on an image patch, multiply elementwise, add up, write one number to the feature map, then slide over one pixel and repeat. (Strictly, the minus signs in the formula flip the kernel before the slide; deep-learning code usually skips the flip and slides the kernel as-is, and since the weights are learned anyway, the distinction changes nothing about what the layer can do.) Because every output is a plain weighted sum of inputs, convolution is a linear operation, and it can even be written as one big matrix multiplication with a highly repetitive, mostly zero matrix.

This is the centrepiece of the lecture. One small image, one $3 \times 3$ kernel, every number real:

Check: apply a 3×3 edge kernel to a patch, by hand

Apply the vertical-edge kernel $w = \begin{bmatrix} 1 & 0 & -1 \\ 1 & 0 & -1 \\ 1 & 0 & -1 \end{bmatrix}$ to the patch $x = \begin{bmatrix} 5 & 5 & 0 \\ 5 & 5 & 0 \\ 5 & 5 & 0 \end{bmatrix}$ (bright on the left, dark on the right). What single number comes out, and what does its sign mean?

Answer. Multiply elementwise and add. The left column contributes $5 + 5 + 5 = 15$, the middle column is multiplied by zeros, and the right column contributes $0 \cdot (-1) \times 3 = 0$. Total: $\mathbf{15}$. The kernel computes "left column minus right column", so a positive response means bright-to-dark going rightward. Flip the patch and you get $-15$: same edge, opposite polarity. Park Fig 3.2's kernel on the bright square's right edge and you will see exactly these $\pm$ responses.

Padding and stride

Two knobs control the sweep. Stride $S$ is how far the filter moves each step: stride 1 visits every position, stride 2 skips every other one and halves the output width. Padding $P$ is how many rings of zeros we add around the border, the same zero-padding as in 1-D, so the kernel can sit centred on edge pixels instead of stopping short; the zeros add no new information. A $5 \times 5$ input with a $3 \times 3$ kernel, padding 1, stride 1 gives a $5 \times 5$ output, the same size as the input, which is why that combination is everywhere. The formula that predicts the output size is coming in section 4; first, feel it:

Fig 3.3, the padding-and-stride explorer. Slide $K$, $P$, and $S$ over a fixed $7 \times 7$ input and watch the kernel positions and the live output size $\hat W = (W - K + 2P)/S + 1$. When the division does not come out whole, the last position does not land flush and the figure says so.

4. Convolutional layers

Now turn the operation into a layer. There are three rungs on the ladder from what we had to what we want. A fully connected layer lets each hidden unit see the whole image: maximum flexibility, catastrophic parameter count, no structure. A locally connected layer restricts each unit to a small region, Idea 1 alone: far fewer weights, but each location still learns its own private detector, so a pattern learned on the left is relearned from scratch on the right. A convolutional layer takes the last step: each unit sees a small region and the weights are shared across all locations. Ideas 1 and 2 together. One filter, slid everywhere, is exactly the convolution of section 3.

One filter detects one pattern, and one pattern is not a representation. So a conv layer applies a whole bank of learned filters, each producing its own feature map, implementing local receptive fields and weight sharing at scale. Each conv neuron computes a linear map followed by an activation, just like every neuron we have met; only the wiring changed. Stack the resulting feature maps and you get the layer's output volume:

Fig 4.1, a filter bank in action. Three filters convolve the same input (all values computed live), producing three feature maps that stack into a $6 \times 6 \times 3$ volume: the next layer's input. Output depth equals the number of filters, and each kernel's depth must equal its input's depth.

That figure quietly answers the two bookkeeping questions students trip on. How deep is the output? As deep as the number of filters: 3 filters, 3 feature maps. How deep is each kernel? As deep as its input: on a grayscale image a kernel is $K \times K \times 1$, on an RGB image it is $K \times K \times 3$, and on the $6 \times 6 \times 3$ volume above, the next layer's kernels are $K \times K \times 3$ again. A conv layer's hyperparameters are therefore: the kernel height and width $K$, the padding $P$, the stride $S$, the depth $M$ (how many kernels, i.e. filters), and the activation function.

Output sizing

Take an input of size $W \times H \times J$ (for RGB, $J = 3$) through $M$ filters of size $K \times K$ with padding $P$ and stride $S$. The output volume is $\hat W \times \hat H \times I$ where

$$ \hat{W} = \frac{W - K + 2P}{S} + 1, \qquad \hat{H} = \frac{H - K + 2P}{S} + 1, \qquad I = M $$

The logic behind the formula is the sweep you watched in Fig 3.3: the padded input is $W + 2P$ wide, the kernel uses up $K$ of that before it can take its first step, and every stride of $S$ buys one more output. Worked on the example from section 3: $W = 5$, $K = 3$, $P = 1$, $S = 1$ gives $\hat W = (5 - 3 + 2)/1 + 1 = 5$. Same size out as in, as promised.

Parameter efficiency: why CNNs win

Now the payoff calculation, the one Fig 0.1 was computing behind the scenes. Compare a fully connected layer against a conv layer mapping the same input size $W \times H \times J$ to the same output size $\hat W \times \hat H \times I$:

$$ \text{FC weights} = W \hat{W} H \hat{H} I J + \hat{W}\hat{H}I, \qquad \text{Conv weights} = K^2 I J + I $$

The FC count multiplies every input coordinate against every output coordinate (plus one bias per output unit). The conv count is one $K \times K \times J$ kernel plus one bias for each of the $I$ filters, and, critically, the image size appears nowhere in it. Make the image bigger and a conv layer's weight count does not move; only the kernel size and the number of filters matter. That is the whole point.

Worked with concrete numbers: 25 million against 224

Map a $32 \times 32 \times 3$ image to a $32 \times 32 \times 8$ output, so $W = \hat W = H = \hat H = 32$, $J = 3$, $I = 8$, and for the conv layer use $K = 3$, $P = 1$, $S = 1$ (which the sizing formula confirms keeps 32).

FC:   32·32·32·32·8·3 + 32·32·8 = 25,165,824 + 8,192 = 25,174,016
Conv: 3²·8·3 + 8                     = 216 + 8               = 224

Identical input and output shapes, and the conv layer uses $25{,}174{,}016 / 224 = 112{,}384$ times fewer parameters. Fewer parameters means less data needed, less overfitting, and detectors that are forced to be reusable.

The code: conv2d from scratch

Everything above fits in a page of plain Python, no libraries. First the sizing helper, which is the formula verbatim: 

def output_size(W, K, P, S):
    return (W - K + 2*P) // S + 1     # e.g. output_size(5, 3, 1, 1) = 5

Then convolution itself: pad, then two loops over output positions, and for each position a little dot product between the kernel and the patch under it: 

def conv2d(image, kernel, stride=1, pad=0):
    K = len(kernel)
    if pad > 0:                        # ring of zeros: no new information
        W = len(image[0])
        blank = [0.0] * (W + 2*pad)
        image = ([list(blank) for _ in range(pad)]
                 + [[0.0]*pad + list(row) + [0.0]*pad for row in image]
                 + [list(blank) for _ in range(pad)])
    H_out = (len(image) - K) // stride + 1
    W_out = (len(image[0]) - K) // stride + 1
    out = [[0.0] * W_out for _ in range(H_out)]
    for i in range(H_out):
        for j in range(W_out):
            s = 0.0
            for a in range(K):         # dot product with the patch
                for b in range(K):
                    s += image[i*stride + a][j*stride + b] * kernel[a][b]
            out[i][j] = s
    return out

5. Going deep: ReLU, pooling, receptive fields

One conv layer gives us a stack of feature maps: filter $m$ produces $z_m = w_m * x + b_m$, and the $M$ maps together become the next layer's input. Feed that into another conv layer, and another, and the thing starting to take shape is a CNN. But two ingredients are still missing, and both come from problems we have already met.

Nonlinearity, or the linear-collapse trap again

Section 3 flagged that convolution is linear. The neural networks lecture proved what happens when you stack linear operations: they collapse into a single linear operation, and the depth buys nothing. Convolutions are not exempt. Two conv layers back to back with no activation between them are exactly equal to one conv layer with a single, slightly larger equivalent kernel. So before the next layer we apply a pointwise nonlinearity, and the standard choice is ReLU:

$$ a_m[i, j] = \operatorname{ReLU}(z_m[i, j]) = \max\{0,\ z_m[i, j]\} $$

Do not take the collapse on faith. The figure below runs both pipelines on real numbers and lets you toggle the activation:

Fig 5.1, why the nonlinearity is not optional. Top path: edge detect, then activation, then blur, two real convolutions. Bottom path: one single 5×5 kernel, computed live by convolving the two kernels together. With the identity activation the two paths agree to machine precision, the stack collapsed. Switch on ReLU and no single kernel can reproduce the result.

Pooling: buying stability

The third promise from section 1, stability, is still unpaid. Convolution alone is precise about position: an eye detector should fire whether the eye sits a few pixels left or right, but its feature map moves when the eye moves. Pooling fixes this by summarizing a local group of activations into one number. Two standard summaries:

  • Max pooling: $y_i = \max_{j \in \text{group}} z_j$. Reports whether the feature is present in the group at all, and ignores everything else. Good when the background matters less, and suited to high-frequency features like edges and textures.
  • Average pooling: $y_i = \operatorname{mean}_{j \in \text{group}} z_j$. Lets every activation contribute, so it preserves background and enforces smoothness when the exact location is unimportant.
def max_pool(fmap, size=2):
    n = len(fmap) // size
    return [[max(fmap[i*size + a][j*size + b]
                 for a in range(size) for b in range(size))
             for j in range(n)] for i in range(n)]

def avg_pool(fmap, size=2):
    n = len(fmap) // size
    return [[sum(fmap[i*size + a][j*size + b]
                 for a in range(size) for b in range(size)) / size**2
             for j in range(n)] for i in range(n)]

The stability claim is testable: shift the input a pixel and see how much the pooled output changes. Do it below, and keep score for both summaries:

Receptive fields grow with depth

Here is the quiet consequence of stacking conv and pooling layers, and it is the reason depth builds a hierarchy. A first-layer unit sees a $3 \times 3$ patch of the image, its receptive field. A unit one pooling layer up summarizes several such units, so it depends on a larger region of the original image. A unit in the next conv layer combines several of those, and its receptive field is larger still. Early layers see edges and textures; later layers, whose receptive fields span whole regions, can respond to parts and objects. Trace it exactly:

Fig 5.3, receptive-field growth through conv 3×3, pool 2×2, conv 3×3. Click any unit in the three computed layers and the exact region of the original image it depends on is computed and highlighted: 3×3 for depth one, 4×4 after pooling, 8×8 at depth three. Depth literally widens what a unit can see.

Translation: what convolution and pooling each buy

Two different translation properties are in play, and naming them separately prevents a very common muddle. Convolution is translation equivariant: shift the input two pixels right and the feature map shifts two pixels right, because the same shared filter computed the same dot products, just elsewhere. The response moves with the pattern. Pooling adds approximate local translation invariance: within a pooling group, a small shift leaves the max unchanged, so the pooled output is roughly unaffected by small translations, which is precisely what Fig 5.2 measured. Together they deliver section 1's stability. Note the fine print, though: these properties help with translation and nothing else. Scale the object up, rotate it, change the lighting, and neither convolution nor pooling promises a thing; the end quiz returns to this.

6. Summary and method card

Three design principles carried this whole lecture. Local receptive fields: nearby pixels are more related than distant ones, so detectors look at small patches. Weight sharing: useful patterns can appear anywhere, so the same detector is reused at every location. Translation robustness: small shifts should not change the prediction, so pooling summarizes nearby activations. Together these are the CNN inductive bias, the assumptions the architecture makes so the data does not have to teach them. That is the deepest lesson here: choosing an architecture is really a decision about the structure of your data. Yann LeCun's insight, the one that made CNNs the default for vision, was exactly that images deserved an architecture of their own.

Method card · Convolutional Neural Networks (foundations)

Model classStructured networks of convolutional filters, nonlinear activations, pooling, and stacked feature maps.

Where this sits in the course story: backpropagation gave us the learning algorithm, and this lecture gave us the first architecture designed around the data itself. The filters in every figure above are the kind of thing backprop learns automatically; nobody hand-designs edge detectors anymore, they fall out of training. Quiz 1

Right. FC weights scale with $W \times H$, which quadrupled. The conv layer reuses the same kernels over a bigger sweep: more computation and a bigger feature map, but exactly zero new parameters. Fig 0.1 is this fact drawn as a curve.
True for the conv layer, false for the FC layer: its weight matrix has one column per input pixel, and the pixel count just quadrupled.
Quiz 2

An input image is shifted 2 pixels to the right. Which statement correctly describes the network's internals?

Convolution is equivariant, not invariant: the shared filter finds the pattern at its new location, so the response moves with it. Invariance only appears after pooling summarizes.
The pre-pooling maps do shift, but pooling groups absorb shifts smaller than the group: the max of the group often does not change. Fig 5.2's counter measured exactly this.
Right, and the two words carry the distinction: convolution moves the answer with the pattern (equivariance), pooling makes small movements not matter (approximate local invariance).
Quiz 3 (transfer): design a filter, predict its feature map

Design a $3 \times 3$ filter that detects vertical edges (bright on the left, dark on the right), and predict what its feature map looks like when convolved over an image containing one bright square on a dark background. Where are the strong positive responses, the strong negatives, and the zeros?

Answer (one good version). Take $w = \begin{bmatrix} 1 & 0 & -1 \\ 1 & 0 & -1 \\ 1 & 0 & -1 \end{bmatrix}$: it computes "left column minus right column", so it responds only where brightness changes horizontally. Prediction for the bright square: a column of strong positive responses along the square's right edge (bright left of the kernel, dark right), a column of strong negative responses along its left edge (dark to bright), and zero everywhere brightness is locally constant, including deep inside the square, because $c - c = 0$ on any flat patch. The top and bottom edges of the square are horizontal changes, which this filter ignores; its transposed sibling catches those. Load the vertical-edge preset in Fig 3.2 and sweep: the feature map is exactly the two opposite-signed stripes. A corner detector follows the same recipe: combine a horizontal and a vertical difference so the response is large only where both change, e.g. positive weights in one quadrant and negatives along both adjoining sides.

Quiz 4 (transfer): the 1×1 convolution riddle

The parting riddle from the lecture: does it ever make sense to use a $1 \times 1$ convolution? A kernel that sees a single pixel surely cannot detect any spatial pattern. When would you use one?

Answer. Yes, and the trick is remembering the third dimension. A kernel's depth always equals its input's depth, so on a stack of $M$ feature maps a "$1 \times 1$" kernel is really $1 \times 1 \times M$: at each location it computes a weighted combination of all $M$ channels. It sees no spatial context, but it mixes across the channel dimension, letting the network build new features out of combinations of existing detectors ("edge here AND red here"). And with $I$ such filters, the output has $I$ channels, so a $1 \times 1$ conv layer changes the number of feature maps: with $I < M$ it compresses the stack cheaply, at a cost of just $1^2 \cdot IM + I$ parameters. Spatially trivial, depthwise powerful.

Quiz 5 (transfer): what convolution and pooling do NOT give you

A colleague says: "our CNN is robust to transformations, convolution and pooling handle that." Explain precisely which transformations the architecture helps with, which it does not, and what you would do about the rest.

Answer. The architecture helps with translation, and only locally at that: convolution's weight sharing makes feature maps shift with the input (equivariance), and pooling makes small shifts approximately invisible (approximate local invariance). Nothing in either operation addresses scale: a face twice as large no longer fits the $3 \times 3$ patterns the early filters learned, and no pooling group restores that. The same goes for rotation, viewpoint, and lighting: the inductive bias simply does not cover them. What to do about the rest is a preview of Part II and of practical deep learning: expose the network to the variation you need (data augmentation with rescaled, rotated, re-lit copies), and build depth, since stacked layers with growing receptive fields (Fig 5.3) can learn features at multiple scales, at the price of learning them from data rather than getting them free from the architecture. The honest one-line summary: CNNs get translation robustness by design, and everything else the hard way.

That is the foundation of convolutional networks: images have structure, so build the structure into the model. Local receptive fields make detectors cheap, weight sharing makes them reusable, convolution sweeps them everywhere, ReLU keeps depth from collapsing, pooling buys stability, and stacked layers grow receptive fields until units see objects instead of edges. Backprop learns every filter. Part II takes these pieces and assembles complete end-to-end vision systems out of them.
